- **Browser attachment uploads stream to disk instead of blocking the server** (Issue #1428): a 9.5 MB attachment sent as base64 inside JSON held the event loop for 181 ms while the server parsed the body, decoded it and wrote the file with a synchronous fsync, stalling a parallel health check by 126 ms. The browser now prepares a bounded upload with `POST /api/uploads` and sends the file as the raw body of `PUT /api/uploads`. The server writes that body chunk by chunk to a staging file in `uploads/` beside the workspace, fsyncs it with the async API and renames it into `files/` before the record commits. A small preview rides along in the grant. An upload whose connection ends early answers `incomplete-upload` and reads in the browser as a lost connection, so a cut upload still offers Retry. The JSON attach routes stay for MCP and API callers, avatar fields keep taking their bytes inline, and the 10 MiB limit now counts the file itself, without the base64 overhead. Gate: `test/upload-stream.test.mjs`.
