- **Sorted table pages stop re-sorting the whole table on every request** (Issue #1093): `query` computed the sort key of every live row on every page, so the first page of a 50,000-row table sorted by a lookup took 81 ms (p50) and 94 ms (p95) over HTTP, and `GET /api/tables/:id` walked every entity in the workspace to count rows (17 ms). The engine now keeps the undressed sort keys, the sorted row order of an unfiltered query and the live row count per table on its row index, and drops all three on every write (`#mark`, `save`, `maybeRefresh`, a rolled-back write). The API shape and the result order are unchanged: `test/query-sort-cache.test.mjs` compares the cached and uncached answers byte for byte across sort directions, nulls, ties, deleted rows, lookups and a rollup, and after every kind of write. `scripts/bench-query.mjs --rows N` builds a scratch workspace and prints p50 and p95 for five requests plus RSS; `test/query-volume.test.mjs` keeps the 50,000-row lookup-sorted first page under its budget in the unit lane.
