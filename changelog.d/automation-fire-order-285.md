- **Automation fire order is stored** (Issue #285): the rules on one trigger fired in whatever order the store read them back. An automation carried no ordinal, the store read the table with a bare `SELECT id, json FROM automations`, and the engine fired `Object.values(state.automations)` in that order, which was rowid order: an accident of insertion that a VACUUM, a hand-edited `.db` or a JSON import could change, and that no surface showed. (A bare `SELECT id` on the same table walks the primary-key index and comes back in uuid order, a third order.) Every automation now carries `seq`, a workspace-wide monotonic counter on `meta.automationSeq` minted at create and never reused after a delete, the same shape as activity's `seq` (Issue #282). It lives in the rule's json, so the SQL schema is unchanged and an existing `.db` opens with no DDL: the engine's open pass numbers every unnumbered rule in rowid order, the order it fired in until now, so no workspace changes behaviour on upgrade, and never moves a number already handed out. The store and the Cloudflare store load automations `ORDER BY` seq (unnumbered last, by rowid); the engine fires and lists by seq, so an import that keeps a dump's key order or a rule a pre-seq CLI appends still fires in order (the straggler last, numbered on the next open). `seq` rides `GET`/`POST /api/automations`, `weave_automations` over MCP, `weave automation list|describe`, and `weave export`/`import`, which keep it and the counter as written; the relation map's pills stack in that order. Gates: `test/automation-seq.test.mjs` (a workspace-wide seq that never repeats; fire order by seq on a `.db` whose rowids return the rules reversed, which fired CBA before this and ABC now; a pre-seq `.db` numbered in rowid order and written through, with no renumber on a second open; the pre-seq straggler; export/import of a dump with its automations listed backwards; route, MCP and CLI parity) and `test/automation-seq-browser.test.mjs` (the relation map stacks a table's rules in fire order).
