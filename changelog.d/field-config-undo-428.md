- **A field configuration change has an Undo and a record in Activity** (Issue #428): a change to a field's options, states, colours, formula, format, default, description, name or type used to save silently, with no toast, no Undo and nothing in Activity. `updateField` is now the one write path for all of them (the field tray, `PATCH /api/tables/:t/fields/:f`, the `Definition` on a `Workspace/Fields` row, `weave_apply_schema`, the CLI and MCP) and it records a `field-config-updated` Activity entry on the table with the definition before and after, the keys that changed and a `seq`. The entries live in the workspace's audit log, so they survive a restart and never ride the table. Saving in the field tray shows the toast with **Undo**, and an entry's own page in Activity has **Roll back**. Both apply the definition before through the same path and write an `undo` entry, and both refuse when the field has changed since. A type change converts the stored values and nothing keeps the old ones, so it is recorded but has no Undo or Roll back, and its toast says so. Removing an option or a state keeps the rows' stored ids, so rolling it back brings their values back. A column width records nothing: in the grid a width belongs to the view. New doors: `POST /api/tables/:t/fields/:f/rollback {activity}` (the schema write's rung), `weave_rollback_field`, `weave field rollback <table> <field> --activity <id>`; the PATCH answer carries the entry id as `activity`.
