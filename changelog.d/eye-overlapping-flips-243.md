- **Overlapping eye flips both reach the table** (Issue #243): flip two switches in the eye while the first flip's PATCH is still out, and both switches move but the table keeps only one of them. Reproduced on `:4400` from `["Chip","Card"]`: two clicks in one tick on Status and Suite left `["Chip","Card","Suite"]`, with Status lost. Every switch PATCHes a whole setting (the hidden set, the system set, the Σ flag). Issue #240 made each handler read the table at click time, but two clicks that both land before either PATCH returns still read the same pre-flip set, and the later write drops the earlier flip. Idle, a round trip is ~20 ms, so this needs load: Issue #216 measured the same tail at 8.7 s. The fix splits a flip into a write and a paint. Writes (PATCH, then the schema reload) go through one queue in click order, and each reads the table only when its turn comes, so the second flip builds on the first. The paint (grid redraw, dock, the popover's rows) stays off the queue, so a PATCH never waits on a render, and only the last flip of a burst paints. One queue covers the hidden fields, the system columns and the Σ row switch. Client only: the engine and its PATCH verb are unchanged. A paint can now land well after its click, so it checks what is on screen first: "last" is judged per table, so a flip in the dock's eye for another table no longer cancels the grid's repaint; only an eye popover on the same table learns the new rows, and it learns its own row set, so a column's ⋮ menu opened since keeps its rows; and the eye's page is redrawn only while it is still the page on screen, so a reader who moved to another table does not get the old one drawn over it. With the first PATCH held open, the second flip went out beside it before the fix (2 PATCHes on the wire) and waits behind it after (1), and the pair now draws the grid once.
