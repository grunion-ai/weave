- **A field type change has an Undo that brings the values back** (Issue #467, following #428): a type change converts every stored value, and until now nothing kept the values from before, so its toast said it had no Undo and its Activity entry offered no Roll back. The write path now keeps each row's value from before the conversion, for rows that held one, with the `field-config-updated` entry. Undo in the toast and Roll back in Activity restore the definition and every row unchanged since the change. A row edited since keeps its edit, converted back to the old type, and a row made since is converted by the same conversion; the toast, the roll back answer (`restored`, `left`, `converted`) and the `undo` entry count each. A field keeps the values of its newest type change only, since the audit log has no size policy and the capped stores cap a count per subject: an older entry keeps its definitions, says its values are no longer kept, and refuses a roll back. The Activity feed, `weave_audit` and `GET /api/audit` show a snapshot as its row count only, and an export carries none, so a credential field's snapshot holds the secret's name at most, never a secret.
