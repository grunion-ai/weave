Card view options

Fifteen ways to lay out the Card view (Feature #175) for one Development/Issue row — Issue #193 as it stands. A–E are round 1 (Feature #181); F–O are round 2 (Feature #184), varying axes A–E left alone: a cover band, a two-column split, a board tile, a sidebar accent, a lifted table row, an icon-led result, a 32px list item, relations first, a date-range bar, and every chip in its edit costume. Every field value is the same chip the table cell and the entity view draw: the state chip with its glyph (category owns the colour), select and multiselect value chips, the relation as a pointer chip with the ↗ mark and no fill, a person as the same pointer with its avatar, a date in the quiet costume the grid gives a plain value, and a +N chip where a row overflows. Light and dark side by side. The matrix compares them on one screen; the note at the foot says which are one renderer under a different config and which need a new shape. Pick one; a separate Feature lands it in the Card renderer.

Which options are the shipped renderer, and which need a new shape

A, B, C, D, E, H, M, O are the same renderView(ref, 'card', { config }) under a different Card config — the contract already carries link, state, description and fields, and viewCardEl draws head, description, foot in that order. What varies between them is only which of those are on and how many fields ride along: H is state: false, description: 'none', fields: [Owner, Due]; M is the configured fields drawn before the head instead of after (one flag on the card tile, fieldsFirst, or a field-order convention); O is the same tile with each chip swapped for the cell's edit control, which the grid already knows how to do (picker-box + picker-pop) — a card-level editable switch, no new markup.

F, G, I, J, K, L, N each change the tile's geometry, so they need a new shape beside chip and card (or a layout key inside the Card config that viewCardEl switches on):

  • F cover — a band above the head that reads the state's --fill; the head loses its state chip to the band.
  • G split — two flex columns; the aside stacks label-over-chip, which no shipped rule does.
  • I accent — a left border in the state's --text and an absolutely placed id; the foot refuses to wrap.
  • J row — inline cells in the table's fieldOrder, not the Card's fields list; the only option that reads the grid's column order.
  • K icon-led — a table-icon slot the card has no notion of today; one field, the table name as a caption.
  • L list item — a fixed 32px single line plus a relation count the renderer does not compute.
  • N timeline — a range drawn as a bar, which is a new value costume, not a chip.

Recommendation: land the config-only four first (H, M, O and any of A–E Kyle picks), then add one layout key to the Card contract for the new shapes rather than minting seven shape values — shape stays the coarse answer to "chip or card", layout the fine one.

Shared by every option: 4px radius on every chip; no fill behind a pointer chip; the chip size from --wv-chip-font / --wv-chip-line; the card's title is the only link, the rest of the tile is inert.
