Three grids, all live — click into one and type. "I want to nav with L and R and tab" is not a tweak, so this is rebuilt around it. ← and → cannot navigate while a cell is a live text input, because the caret is already using them — the previous round claimed both and could only have one. Wanting them for navigation means cells rest as values and open on purpose.

What that decision hands over, including two things you did not ask for
  • All four arrows and Tab navigate the grid at rest. The thing you asked for.
  • Keyboard row selection comes free. Space is unclaimed at rest, so it picks a row up, ⇧↑⇧↓ extend and ⌘A takes the table. Last round that needed a mode and a whole extra direction to pay for; now it falls out.
  • Hover finally has a job — showing the control a click would open, rather than every cell wearing one at once.
  • Still true from before: one click edits whatever the type and a checkbox flips on that click; ⌘-click toggles a row and ⇧-click takes the run; Return commits down the column; ⇧Return makes the next item; ⌘Return opens the record as a page.

Which leaves one question, and it is the only thing the two challengers disagree about: when a cell is open, do ← and → still navigate? REST says no — the caret takes them back. EDGE says yes, and steps out of the cell when the caret runs out of text.

NOW

What ships today

Feature #133 · Ledger

Every cell wears its editor permanently, which is why ← and → are already spoken for: they belong to a text caret in whichever cell you are standing in. A click lands in the field it hit, ⌘-click opens the side peek, and the #id ↗ link navigates. The grid answers to no keys and has no notion of a selected row — press Tab, an arrow, or ⇧Return in the demo and watch nothing happen.

WinsNothing to learn, nothing to build. One click has always reached every field, checkbox included — that part was never broken.
FitsReading a table and correcting a field in passing, which is most of what the grid is used for today.

What it is missing

    REST

    Resting cursor · the caret takes ← → back

    Excel · Airtable

    Cells rest as values, so all four arrows and Tab navigate the grid. Return, a click, or just typing opens a cell — and while it is open, ← and → go back to the caret until you Tab, Return or Esc out. The conventional split, and the one nobody has to be warned about.

    WinsEvery key means one thing in each state, and the states are the ones every spreadsheet already taught. No surprises, nothing to explain.
    FitsAlmost everything. The safe answer, and the one to pick if you are not sure.

    What we lose

      EDGE

      Edge-through · ← and → always navigate, eventually

      the literal reading

      The strict answer to "nav with L and R": those keys never stop being navigation keys. Inside an open cell they walk the caret, and the press that would run past the end of the text steps into the next cell instead. Try it in the demo — put the caret mid-word and press → until it falls out the far side.

      WinsYou never have to think about which state you are in, and a row of short values can be walked end to end without ever reaching for Tab.
      FitsDense tables of short values — dates, amounts, statuses — where the caret rarely has far to travel.

      What we lose

        Do we need peek?

        Counted rather than argued, because the repo already answers it.

        No — and dropping it is what makes ⌘-click free

        The peek is a second way to render a record, kept for a caller that does not exist. Its own upgrade is what did it in: you asked for "panel when open should not be preview but the full entity" (#39), so the peek became the entity — and then #117 decided the entity belongs on a page. What is left is the same view twice, with five inPeek branches threaded through renderEntityView to keep them apart.

        The honest argument for keeping it is scroll position — the table stays where it was while you read a record. #117 already weighed that against a full page and chose the page. If that call still holds, the peek has nothing left to do.

        1. Delete peekEntity (~56 lines), its 17 CSS rules, and the five inPeek branches in renderEntityView. The entity page is unaffected — it is the same renderer without a second layout mode.
        2. ⌘-click becomes free, which is exactly what H and K want it for. Nothing relocates, and ⌘Return opens the page.
        3. Watch the one thing it was good at. If losing your place in a long table starts to hurt, the answer is a back-to-table affordance on the entity page, not a second renderer.

        Recommendation

        Build REST. Ship EDGE behind a setting if the corridor turns out to be worth it.

        Both give you what you asked for: at rest, ← → ↑ ↓ and Tab all navigate. They differ only once a cell is open, and there REST is the one that never surprises anybody — the caret owns the horizontal arrows, exactly as it does in every text field on the machine.

        EDGE is the stricter reading of what you said, and its appeal is real: a row of short values walks end to end with one key. Its problem is that the keypress which leaves the cell is indistinguishable from the one before it, and an empty cell is at both edges at once — so a run of blanks becomes a corridor you fall through. That is worth having, and worth having deliberately, which is what a setting is for.

        1. Cells rest as values; hover arms them. The click path is unchanged from today, so activateCell is already correct — it just gets called on an armed cell rather than a permanently live one.
        2. One keymap. At rest: arrows and Tab move, Space selects, Return or any character opens. Open: Return commits down, Tab commits across, Esc reverts.
        3. Selection, now free on both sides. ⌘-click and ⇧-click from the pointer, Space and ⇧↑↓ from the keyboard. This is what last round needed an entire extra direction to buy.
        4. Drop the peek in the same change — see below. That is what makes ⌘-click free, and it deletes a second rendering of a record rather than adding one.
        5. Then the puck bar of #132, which now has a selection to act on from either hand.
        6. EDGE as a per-table or per-user setting, once REST is in. It is one branch in the open-cell keymap, so it is cheap to add and cheap to withdraw.

        Still open

        QuestionWhy it matters
        Do ← → step out of an open cell?The only thing separating REST from EDGE. REST never surprises; EDGE never makes you think about a state. One branch in the open-cell keymap either way, so it can be a setting rather than a verdict.
        Does ⇧-click take a run of rows or a rectangle of cells?Rows is the smaller build and matches the puck bar of #132. Cells opens the door to fill-down and paste later, and cannot be retrofitted cheaply.
        Where does the docs-chips column sit in the arrow and Tab order?Documents are not cells. Skipping them keeps the run tabular; including them makes one stop a chip rather than a field.
        Does a resting grid still read as editable?The reason every cell wears a control today. Worth watching on a table of mostly-empty fields, where hover is the only thing saying they can be filled in.
