Every grid below is live — click into one and type. Same four rows, same five fields, seven different bargains about what a keystroke means. The strip under each grid names the verb the pattern just resolved, so you can feel the difference between Return that walks down a column and Return that opens a record. Today's weave sits at A minus the keyboard: the #id ↗ link navigates, a click on a cell raises that field's editor, ⌘-click peeks — and nothing responds to Tab, ↑↓, or ⇧Return. Each direction below decides what to spend those keys on — and G, the last one, spends a click instead, with its bill itemised.

A

Ledger+ · focus is the cursor

extends today's weave

One state, not two. Every cell already wears its editor, so the browser's own focus ring is the cell cursor and there is no mode to be in or leave. Tab walks the row and wraps into the next; ↑↓ walk the column; ←→ stay with the text caret where a typist expects them. Row selection does not exist — the price of never having a mode.

WinsSmallest delta from what ships today; nothing to teach; the caret never gets stolen mid-word.
CostsNo bulk anything — no multi-row delete, no fill-down, no "set these six to Building".
FitsTables you read and correct one field at a time. Registries, config tables, small sets.
B

Two-mode · navigate, then edit

Airtable · vim

The grid is a map until you say otherwise. In nav the arrows move a cell cursor and Space is free to pick up a row; Return or any printable character drops into edit, where the arrows go back to the caret and Esc returns you to the map. Two states buys the entire modifier space: ⇧↑⇧↓ extend a run, ⌘A takes the table, Esc drops the run.

WinsRow selection, range operations, and type-to-replace all come free. The model every spreadsheet user already has.
CostsMode error is real — typing into a grid that was in nav mode fires commands instead of characters. Needs a loud mode indicator.
FitsThe general-purpose answer. Data entry and bulk edit in the same surface.
C

Row-first · the record is the unit

Linear · Superhuman

The cursor sits on a row, not a cell. ↑↓ (or jk) move between records, Return opens one, x picks it up, ⇧↑⇧↓ take a run. Cells are reachable but secondary: → descends into the row, Tab is trapped inside it, and Return or Esc climbs back out. The grid becomes an inbox.

WinsFastest scan-and-open in the set; selection is one key with no mode; matches the muscle memory of every issue tracker.
CostsTwo keystrokes of overhead before you can type into a cell — punishing for a table you are filling in rather than triaging.
FitsTask and ticket tables, anything where you open records more often than you edit fields in place.
D

Spreadsheet · rectangular ranges

Sheets · Excel

B's two modes with a real range underneath. ⇧ plus any arrow grows a rectangle, ⌘ plus an arrow jumps to the edge of the data, ⇧Space takes the row and ⌘Space the column. Once a range exists it becomes a container: Tab and Return wrap inside it, and ⌘C/⌘V move the block. The only direction where pasting a spreadsheet into weave works.

WinsPaste-from-Excel, fill-down, block clear. The bulk-import path nobody has to be taught.
CostsThe largest build here by a distance — clipboard shape, edge jumps, range-locked traversal, column headers as selectors.
FitsImport-heavy tables. Wrong reach if the first job is triage rather than tabular data.
E

Command-led · the grid reads, ⌘K writes

Raycast · agent-native

Spend almost no keys on the grid. ↑↓ move, Return opens, x selects, and everything else — set a field, change state, add a row, bulk-apply across a selection — goes through ⌘K scoped to whatever is under the cursor. One vocabulary for a person and for an agent, since a command is a thing the MCP server can also call.

WinsA tiny keymap that never collides; bulk edit is the same gesture as single edit; every action is nameable, loggable, replayable by an agent.
CostsSlowest per-field entry in the set. Typing a value takes a palette round trip, so filling a fresh table is miserable.
FitsAgent-first tables and bulk state changes. Pairs with A or B rather than replacing one.
F

Form-fill · the table has no bottom

Notion databases · invoice entry

Tuned for one job: getting rows in. Tab walks every editable cell in reading order across the whole table, and Tab off the last cell creates the next row and keeps going, so a typist never stops to reach for a +. Return commits and drops to the same column one row down for column-wise entry. Esc reverts the field rather than exiting a mode, because there is no mode.

WinsHighest keystroke efficiency for entry; a hundred rows never require the mouse.
CostsAccidental rows at the end of every Tab run; selection is mouse-only; no bulk verbs at all.
FitsIntake tables — deals, expenses, contacts — where the table exists to be filled rather than browsed.
G

Two-click · click selects, click again edits

Finder · Excel · Kyle, 2026-08-24

The pointer carries the mode switch instead of a key. One click selects the cell and tints its row; a second click on that same cell opens that field's own editor or dialog — a date gets the calendar, a select gets its picker, a relation gets record search, routed through the cellActivation map weave already ships. Return is a toggle: from rest it opens the cell, from an open cell it locks — commits and settles, without walking down the column. Tab and the arrows navigate; ⇧Return makes the next row.

Reverses a shipped ruling. Feature #133 (Ledger, 2026-08-24) settled that a single click raises that field's editor, because a bare row click "fought the cell it landed on". G walks that back one notch — the first click now selects. Worth deciding on purpose rather than drifting into.
WinsRow selection costs no key at all — clicking is already selecting. The grid becomes safe to click around in. Every field type reaches its own dialog by the same gesture. It is the model Finder and Excel already taught everyone.
CostsSeven of them, itemised below — the headline is a click on every edit, forever.
FitsTables you browse and correct rather than fill. The best answer if row selection matters and a keyboard mode does not appeal.

    Recommendation

    G is the better answer than my first one — with its bill paid on purpose

    My earlier pick was A now, B later. G beats it on the question that was actually hard. Row selection kept forcing a second state, and every way of buying that state cost either a printable key or a keyboard mode. G pays with the pointer instead: clicking a cell already selects it, so selection arrives free, and the mode switch is a gesture people learned from Finder and Excel rather than a rule they have to be taught.

    The thing to decide deliberately is the reversal. Feature #133 ruled a single click raises that field's editor; G makes it take two. That is a real regression for the one job weave's grid is best at today — reading a table and correcting a field in passing — and it is the first cost in the list above, not a footnote.

    1. Decide the reversal first. Is one click worth spending to make selection free? If no, stop here and ship A — nothing below matters. If yes, G is the shape.
    2. Exempt the cheap types, and say so. A checkbox should still flip on one click, and the #id ↗ link still navigates. The rule becomes "one click selects, except where the whole cell is the control". Uniformity loses; a grid that takes two clicks to tick a box loses harder.
    3. Keep the keyboard from A. Tab, the arrows and ⇧Return behave the same under G, so the four handlers are the same work either way. Build them first and they survive whichever way the reversal goes.
    4. Then the selection, which is now nearly free. Clicking already tracks a cell and a row; the puck bar of #132 needs the row set and a select-all box, not a new interaction model.
    5. ⌘K over the selection last (E's lane), so "set Stage → Building" works on six rows and reads identically from the MCP server.
    6. Still not now — D. Rectangular ranges are a feature, not a keymap. C and F each stay reachable later as a per-table preference.

    The hedge, if the reversal bothers you: keep single-click-to-edit as today and add ⇧click and a hover checkbox column for selection. You lose G's uniformity and gain back the click — the same trade read from the other end.

    Open questions for Kyle

    QuestionWhy it forks the build
    Does Return open or commit?The single biggest fork. Commit-down (A/B/D/F) treats the grid as a sheet; open-record (C/E) treats it as an inbox. Everything else follows.
    Is one click worth spending to make selection free?The G question, and now the first one. Two clicks to edit is the price; row selection with no key and no keyboard mode is what it buys. Everything else in G follows from this answer.
    Is row selection worth a keyboard mode?Only live if the answer above is no. Selection without a mode means stealing x or Space from typing; with a mode it means mode error. G's answer is a third option — spend the pointer.
    Do checkboxes and links get an exemption?A checkbox that needs two clicks to tick is worse than an inconsistent rule. Exempting the types where the cell is the control keeps G usable and costs its uniformity.
    Does Tab at the end of the table create a row?F's infinite grid is the fastest entry model here and the easiest to trigger by accident. Worth a per-table setting rather than a global answer.
    Where does the doc-chips column sit in the Tab order?Documents are not cells. Skipping them keeps the Tab run tabular; including them makes the last stop a chip, not a field.
